Maintenance

Compact first, then clean up.

A maintenance run on an Apache Iceberg table compacts first, then cleans up, in one fixed order. The order is defined in code; no preset can change it.

Why maintenance matters

Apache Iceberg's table format is genuinely excellent — hidden partitioning, snapshot isolation, schema evolution, engine-agnostic metadata. What it doesn't give you is any promise those things stay fast. Left alone, four things rot.

Compaction is not one operation

Teams pick a compaction strategy based on write pattern and query filters — the same primitive (optimize) does very different work depending on which one runs.

Canonical order

Planner chunking

Ranked partitions become a chunk under a GB budget, an oversize partition alone, or a small-table bypass. The planner picks one of three paths per run.

Admission — load-aware, never eager

Three guardrails, always on

Destructive operations are guarded. expire_snapshots and remove_orphan_files require the relevant tier in the scanner. Cryo never touches snapshots the retention policy would keep.
