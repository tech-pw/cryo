Architecture

Cryo sits between Apache Iceberg catalogs on the read side and engines on the write side. Sources never reach destinations without going through the plan.

Where Cryo sits#

Cryo is a maintenance control plane for the lakehouse you already run. It does not replace the catalog, Trino, Spark or object storage. Operators, catalogs and engines sit on the left; Cryo is the middle; the lake stays on the right.

System context#

The scanner only reads sources. Workers only execute on destinations. PostgreSQL holds durable state, Redis holds the queue and the locks, and object storage holds the table data.

Scheduled maintenance#

The scheduler enqueues work for presets that are due. The governor probes live engine load and admits jobs. A worker asks the planner for a plan, the engine executes it, and the result is written to the audit log.

Job lifecycle#

Nothing runs until the governor admits the job. A failure stays on that table and the run continues. A deferred job goes back to the queue and is retried when its window opens.

The run view groups jobs by how they ended. The seeded demo run shows 9 jobs: 8 completed, 1 failed and 1 skipped, and the failed job stays on its table.

Assignment#

Assigning a preset to many tables sends a filter spec, never a page of table ids. The API resolves the filter, shows a preview, and only then creates the binding.

Component jobs#

ComponentJobBoundary
ScannerReads sources and stores the shape of every table. Runs from a CronJob and from an ad-hoc scan queue.Never reads data files. Never starts a rewrite.
PlannerTurns stored table shape into ordered operations with partition predicates.Engine-agnostic. Emits no SQL strings. Operation order is fixed in cryo/planner/guardrails.py.
SchedulerFinds due presets and enqueues jobs.Leader-elected. Several replicas may start, one is active.
GovernorDecides whether and when a job may run. Probes live load (system.runtime.queries for Trino, slots for Spark on EMR), applies per-replica caps and round-robins across replicas.Leader-elected. Honors cooldowns and off-peak windows. Bounds real concurrency, so more workers do not mean more parallel rewrites.
WorkerExecutes one table's maintenance on one destination engine.Holds a per-table Redis lock for the job's lifetime. A failure is recorded and the run continues.
API and web UIThe API serves tables, runs, presets, assignments and audit. The UI is a client of the API.The UI talks only to the API.
