What decays in an Iceberg table, and what Cryo runs for each

Nothing here is a bug. It is what normal writes leave behind. Rows follow the order Cryo runs them in: compact first, clean up after.

Delete files

Row-level updates and deletes write separate delete files. Every read has to merge them back into the data, so reads slow down as they pile up.

→
convert_deletesrewrite_position_deletes
rewrite_position_deletes is Spark only

Small data files

Each streaming write or small batch adds another tiny Parquet file. Queries open thousands of them, and every open is an S3 request you pay for.

→
optimize
Trino OPTIMIZE · Spark rewrite_data_files

Column statistics

Stats drift as data changes. The query planner then guesses row counts wrong and picks worse join orders.

→
compute_statistics
Trino ANALYZE · Spark compute_table_stats

Manifests

Each commit adds manifest files that list the data files. Planning a query reads them before it touches any data, so planning slows down too.

→
optimize_manifests
Spark rewrite_manifests

Snapshots

Every commit is a snapshot, and it stays until something expires it. Old snapshots keep files alive that you deleted long ago.

→
expire_snapshots
Keeps a retention window plus the last N

Orphan files

Failed or aborted writes leave files that no snapshot references. Nothing can read them, but they still sit in S3 on your bill.

→
remove_orphan_files
Only files older than a safety threshold
The scanner finds each of these from catalog metadata alone. It never reads your data files. Order defined once in cryo/planner/guardrails.py
